# Bounded employer source refresh

The web app accepts recent issuer-file listings, not proof of complete plan coverage. The old `tic:load` importer deletes existing rows before replacement finishes; do not use it for unattended production refreshes.

`scripts/tic-refresh.ts` prepares, validates, and publishes one selected issuer file. It does not select nationwide coverage, certify negative answers, schedule itself, or replace Medicare data.

1. Resolve the issuer's current table of contents through its official transparency site. Archive the TOC and selected rate file locally; record URLs, observed source dates, and download receipts in the storage manifest. Keep large files outside Git and the web service. Check the intended mounted volume, capacity, and free-space floor before downloads.
2. Install the locked extraction tools with `npm ci --prefix tools/tic-ingest`. Run `node --import tsx scripts/tic-refresh.ts --action prepare --source <local-rate-file> --source-url <original-https-url> --toc <local-toc> --toc-url <original-https-toc-url> --out <local-publication-directory>` using the repository's Node version.
3. Preparation verifies that the source URL appears in the archived TOC, preserves its plan mappings, extracts memberships without an NPI allowlist, and emits a hashed `publication.json`. The standalone memory-backed preparation remains conservative; scheduled limits are specified below. TOC limits: 10 MB compressed/100 MB decoded TOC, 200,000 memberships and 30,000 plan links. A single local ZIP32 JSON member is streamed with CRC, decoded-length and source-stability verification; ZIP64, encryption, multiple data members and unsafe layouts are rejected. Files requiring external provider references are rejected until those references can also be archived and verified. This is intentionally a bounded publisher, not the national streaming pipeline.
4. Validate with `--action validate --receipt <publication.json>`. Test the real candidate against a disposable loopback database using `scripts/eval-tic-publication.ts` and `AFFINITY_TIC_PUBLICATION=<publication.json>`. That evaluator requires the dedicated database `affinity_employer_e2e`; it deletes only synthetic test records there.
5. For an authorized production publication, supply `DATABASE_URL` securely and run `--action publish --receipt <publication.json> --expected-host <exact-database-host> --result <protected-local-result.json>`. External connections require `sslmode=require`. Never place credentials in arguments, screenshots, receipts, Git, or the public-data SSD workspace.
6. Check the committed file ID, actual database counts, dated positive source listing, unknown missing-provider result, plan search and public page. Remove the temporary connection bridge and close temporary access surfaces.

## Publication and recovery contract

Raw source, TOC, and membership SHA-256 hashes are checked before initial acceptance. Later publication or replay may authenticate a previously accepted raw source through the Mini-local compaction proof described below; TOC and normalized bytes are still rehashed. Every row must share the selected source URL, date, entity and schema; malformed or mismatched records fail rather than being skipped. The plan mapping must still equal the archived TOC. Duplicate membership keys fail the transaction.

The publisher adds a new file and all its memberships/plan links in **one database transaction**, under an advisory publisher lock. It reads back counts before commit, rechecks membership bytes, and leaves every existing file untouched. A failed batch rolls back the entire new file. An already indexed URL fails closed; replay never replaces data silently. A publication may be valid for one file while its plans remain only partly indexed.

The result records the exact new file ID and source URL. If a committed publication must be withdrawn, first verify both against that result and recheck the intended database. Delete only that newly added file ID in a transaction; its memberships and links cascade. Existing sources are untouched, and the archived, verified candidate can be published again if appropriate. Do not delete older datasets as part of this bounded workflow.

The standalone publisher makes no paid resource changes. The managed Mini cycle below adds scheduling support, idempotent replay and restricted retention. Nationwide selection and complete-plan certification remain outside this bounded pipeline.

## Mini schedule and removable SSD

The local Codex heartbeat `affinity-mini-issuer-refresh` checks daily at 06:00 Eastern. It creates no Render cron service. The Mini owns orchestration; the SSD is optional between processing runs and is never part of public request serving. A disconnected SSD is an expected deferral, even if it is attached to no computer.

Before SSD I/O, run `node scripts/check-refresh-volume.cjs` and require JSON `state: ready`. The read-only guard verifies the actual mounted volume UUID, mount point, writable state and 150 GB available-space floor. It never creates `/Volumes/dev`. An absent, wrong, read-only or low-space disk returns `deferred`; callers must not treat exit code zero alone as permission to process. The separate 100 GB aggregate task-data cap still applies.

Store only small orchestration checkpoints on the Mini internal disk at `~/Library/Application Support/affinity/refresh/status.json`; keep raw/normalized bulk data on SSD. Never substitute an internal-disk folder for an absent mount. Defer until the next daily run, without repeated unchanged alerts. Warn if deferral threatens the source freshness window (within seven days of the 60-day limit).

Recheck identity before each write phase and publication. If storage disappears mid-run, abandon incomplete candidates and preserve last committed production data. Revalidate hashes/counts after reconnecting; incomplete downloads must restart unless a validated resume mechanism exists. After an uncertain database commit, read back the exact source/file identity before retrying. Local receipt loss is not proof that a transaction failed. Existing freshness checks continue aging evidence into unknown; never alter dates to hide a missed refresh.

Volume deferral, download interruption and transaction rollback are tested with injected faults. No physical disconnect was performed. The pipeline does not claim that every issuer file fits its bounds: unresolved names, oversized files and unsupported indexes remain explicit blocked inventory.

## Unattended publisher implementation

`npm run refresh:employers` runs the deterministic cycle on the Mini. `-- --issuer mmoh` or `-- --issuer cigna` selects an issuer for an owner drill. Run with the locked Node 24 runtime and installed root/tool dependencies. The cycle uses a single OS-released SQLite lock with a PID sidecar, rechecks SSD identity, archives discoveries, validates complete candidates, publishes under the database transaction lock and saves a small internal-disk status receipt. Unchanged managed sources require a matching upstream ETag, unchanged current plan mappings, local archive validation and database count readback. Missing receipt after commit is reconciled through the database ledger.

A dedicated `affinity_refresh` database role has SELECT/INSERT/DELETE on the four base TiC publisher tables plus the five compact-index/shared-plan tables installed by the guarded web startup. UPDATE rights remain limited to activation/withdrawal flags; the role has no role/database creation or superuser rights. Its connection is stored in `~/Library/Application Support/affinity/refresh/database.json`, owner-only mode 0600 within a 0700 directory. The runner checks owner, permissions, destination, role and TLS before use. No credential belongs in the repository, SSD, CLI arguments or scheduler prompt. `scripts/setup-refresh-credential.ts` is a one-time owner setup tool, not a daily job; it refuses to rotate an existing role blindly and removes its protected temporary input.

The `TicRefreshPublication` ledger binds content identity, logical source, file ID and the local recovery receipt. Signed URL query changes do not create new content identities. A changed upstream ETag or plan mapping triggers complete revalidation, even at the same source date and URL. Publication refuses a source-date regression. Per logical source, current plus one preceding managed generation remain in Postgres. Only the active generation participates in readiness, plan search and provider answers. Activation and deactivation share the insertion transaction, so retained rollback evidence cannot contribute superseded positive listings. Older managed generations are retired transactionally only after archive hashes and ownership are verified. Legacy sources are never automatically retired. Archival age does not invalidate historical rollback bytes. After a successful retirement transaction, hash-verified raw and normalized files belonging to retired managed generations may be reclaimed. The separate authenticated raw-compaction path below can also reclaim a new owned raw download while preserving its normalized current/rollback evidence. Current ledger references protect shared bytes; TOCs, publication receipts and a deletion manifest remain. Cleanup failures are explicit review items and never undo a successful publication. Legacy archives and shared parent TOCs remain under the aggregate SSD cap; reaching that cap defers processing.

Cloud capacity stays fixed: the runner refuses a new publication when current database bytes plus a conservative row/index staging estimate exceed 2.5 GB on the existing 5 GB disk. A verified existing publication can replay without a new-row reservation. This deliberately leaves space for WAL, bloat, rollback and other app tables. It neither upgrades resources nor enables disk autoscaling. This is an application budget, not a measurement of filesystem free bytes; operator observation of the Render disk remains part of deployment review.

`npm run eval:refresh-recovery` requires the disposable loopback database `affinity_employer_e2e`. It proves rollback after a simulated storage disconnect during an insertion batch, two-generation retention, legacy preservation, idempotent recovery after loss of a local commit receipt, refusal to prune with a corrupt archive, and withdrawal of the latest generation. Unit tests also cover interruption during download, restart of partial files, volume identity, free space, read-only storage, bounded response size and strict provider-reference closure. These are fault-injection tests, not a physical unplug test.

The scheduled runner uses the SSD-backed path below: up to 5 GB per source archive, streamed with byte and declared-length checks and a 30-minute download deadline. The standalone CLI preparation described above retains its 150 MB memory-backed path. The legacy row publisher retains its 200,000-membership cap; the opt-in exact NPI representation below accepts larger complete sources. Both enforce the 30,000-plan limit and reject unresolved references or overflow.

Issuer URLs are indexed rather than unique: one URL may serve multiple historical content versions. The legacy loader is restricted to loopback fixture databases. `withdrawManaged` requires an exact active managed file ID, marks it withdrawn and atomically reactivates the retained predecessor; withdrawn content cannot silently replay or be selected as the next rollback generation.

Large Anthem TOCs use `tools/tic-ingest/selected-toc.ts`: disk-backed mapping, complete gzip/JSON EOF, parent SHA-256, exact source plan metadata and bounded per-source projections. The publisher binds each projection to the complete parent and receipt; within one process parent hash checks are cached only while device/inode/size/mtime/ctime are unchanged. An omitted issuer plan name stays absent in the source projection and empty in the serving record; the UI labels the missing name explicitly. Identifiers remain required. No synthetic plan names, negative network claims, or national completeness are inferred.

The compact Anthem projection scope is explicitly captured in the Mini's protected `anthem-plan-scope.json`: 2,522 previously indexed employer identities, including the four discovery EINs. Complete nationwide mappings exceeded the 30,000-plan per-file serving cap on the real November source. The full source is retained locally; projections preserve every matching source plan object for the explicit identity set and record excluded/unresolved selections. The scope does not silently expand in daily runs. Changing it invalidates the projection cache and requires revalidation. It does not imply that an employer plan or national network is complete.

The Mini heartbeat invokes the owned pinned worktree through `scripts/run-mini-refresh.sh`, rather than reimplementing discovery in a chat. The wrapper validates Node24.22.1+, fixes its working directory and holds an idle-sleep assertion. Overlap is an expected deferral. The runner preserves source-date checkpoints and distinguishes actual insertion from durable replay. Repeated reference IDs are expanded once per source after closure validation; duplicate definition IDs are rejected in strict mode.

The standalone memory-backed extractor retains conservative memory budgets (16 MiB per group/reference, 64 MiB total reference accounting). Scheduled extraction uses bounded SSD catalogs instead. The small worker supervisor records abnormal exits without overwriting another run. Cached Anthem lineage retains its original URL; renewed official transport signatures are accepted only for the same object identity.

## SSD-backed processing

The larger-input path keeps provider references and normalization scratch on the verified SSD. Local input limits are independent of publication limits: 5 GB source archives, 4 GB scratch (8 GB with compact serving enabled), 128 GB decoded bytes and two hours of extraction time. Each attempt reserves its complete workspace before I/O. Daily execution attempts at most 64 new candidates by default, while still replaying accepted sources and reporting cached blocks; the whole cycle has a four-hour deadline.

An owner-run preparation may select a smaller scratch cap through `preparePublication`'s `disk.maxScratchBytes`. The override must be a positive safe integer no larger than the existing mode limit; it never relaxes complete extraction, source freshness or publication validation. The daily publisher remains serialized. Any separate local preparations need a combined workspace reservation and isolated receipts; their shared-state registration and cloud publication must use the publisher lock.

The legacy row cloud contract remains 200,000 memberships per source. Both representations retain 30,000 plan links and the conservative 2.5 GB database staging budget. A capacity receipt records the measured starting size and reservation before a new publication; the transaction independently rechecks. Larger local inputs do not authorize paid resource changes or partial/truncated uploads. See the [measured acceptance receipt](evaluation/2026-11-04-ssd-large-source-processing.md) for current installation and source status.

Complete preparations blocked by capacity remain on the SSD, with a small protected internal index. An unchanged source ETag and processing policy permit reuse only after validating the archived receipt, source identity, hashes and current plan mappings. Reuse avoids another download/extraction and does not spend the new-candidate allowance. A source without a usable validator still requires fresh source evidence. Full-GET hash-proven unchanged replays refund their provisional attempt. A committed publication whose prepared checkpoint survived a crash is recognized through the active receipt/content identity and does not reserve duplicate rows.

Monthly Cigna partitions and Anthem month-only filenames share their respective retention identity. Existing ledger keys are reconciled on read, without a destructive migration. Three-generation rollover retains the current source and one rollback version; only verified owned oldest bytes are reclaimed. Network/file identities remain distinct.


## Authenticated raw compaction

After complete strict extraction, the Mini may reclaim only its new per-run raw download. The normalized memberships, exact TOC/parent/lineage, original source date and hashes, extraction limits and engine revision remain. A private 32-byte Mini key authenticates the original source receipt plus EOF, archive-integrity, reference-closure and source-stability acceptance. The seal means local extraction acceptance only; it does not assert database publication or complete plan coverage. Complete capacity-deferred preparations may also be compacted and reused after all current mapping and freshness checks.

The key lives at `~/Library/Application Support/affinity/refresh/source-proof.key` with mode 0600 under the protected 0700 state directory. Owner setup creates it exactly once; daily runs never regenerate it. Missing/wrong keys or unsupported semantic policies fail closed. Keep this key for every retained seal; it is not sent to Render, Air, Git or Notion. Install the compatible validator before enabling compaction; older runtimes cannot validate missing raw sources. Rotation or parser-policy migration requires a separately verified key/evidence migration or reacquisition of the original bytes.

Deletion follows fsynced evidence, a signed pending-delete proof, durable publication-receipt replacement, revalidation, and a durable removal manifest. Exact source inode, timestamps, hash and size, owned directory identity, SSD identity and all ledger/prepared references protect removal. A crash before deletion preserves raw; a crash afterward leaves authenticated recoverable evidence. Reentry never fabricates acceptance for an unsealed missing source. Legacy/baseline originals are not eligible. APFS clones can free zero physical bytes; live filesystem free-space checks and full reservations remain mandatory.

Rejected extraction has a separate diagnostic-only removal receipt. It cannot authorize publication. Only an exact complete hashed new download with no publication/prepared receipt and no retained raw reference can be reclaimed. Partial or ambiguous downloads and unavailable SSD cleanup remain explicit recovery items. No arbitrary directory sweep occurs. Run `node --import tsx scripts/eval-compacted-refresh.ts` only against the disposable loopback `affinity_employer_e2e` database for real publication/replay/retirement/rollback checks.

## Exact compressed NPI serving

`npi-prefix-v1` stores the complete unique NPI set in four-digit prefix buckets, with sorted six-digit suffixes encoded as UInt32LE and deflated. This is lossless for the public provider-listing query. Full NPI/TIN memberships remain in the verified SSD archive. No sampled/truncated source, negotiated prices, or claim of plan completeness enters the serving index. Absence remains unknown.

The explicit compact mode permits up to five million complete local membership pairs, eight GB scratch, ten thousand buckets and 32 MB encoded payload per source. Every bucket and the full ordered NPI set are hashed. Publication independently compares the compact set with every validated normalized row, writes an immutable index, verifies every stored payload against the exact manifest, then atomically activates the generation. Routine publication/replay computes each payload SHA-256 inside Postgres and returns only hashes, lengths and counts; the validated local manifest proves the exact NPI set without repeatedly sending compressed indexes back to Mini. Withdrawal without an expected local receipt still decodes and verifies the full retained index. Existing row generations remain supported. New allocation reserves three times encoded bytes, bucket/plan overhead and 16 MB headroom under the unchanged 2.5 GB gate; it does not resize Render. Public lookups decode at most 16 MB per request and withhold unsupported/corrupt evidence.

Derived serving fields are deliberately excluded from the raw-source HMAC: the original source/date/TOC/normalized evidence remains authenticated, and serving is separately recomputed and checked against that authenticated evidence. Adding a representation writes `compact-publication.json`, preserving the original receipt. It cannot change the source date, plans, normalized hash, or freshness. Historical receipts and legacy fingerprints retain their original identity; compact fingerprints also bind format and manifest hash.

The two additive tables are initialized by the existing web service's guarded `prestart` script using its existing database role. The exact production service/database are allowlisted; the only test target is the disposable loopback database. Startup refuses readiness if schema initialization fails. The restricted Mini role receives only SELECT/INSERT/DELETE on these tables. No new Render service, job, disk, instance or plan is created.

Install Mini's protected `compact-serving.json` only after the new release is live and `/api/health` confirms `ticServingFormats: ["npi-prefix-v1"]`. Every enabled cycle checks that capability before publication. Missing opt-in retains legacy behavior; unavailable/incompatible serving fails closed. For application rollback, first withdraw compact generations to compatible retained data or keep the dual reader; an old row-only reader cannot answer new compact generations. A reader-only rollback must never be advertised as preserving compact coverage.

Validation: `tests/tic-compact.test.ts`, the full app suite, and `scripts/eval-compact-tic.ts` against the disposable local database cover exact set preservation, corruption, raw compaction, idempotent publication, generation retention and withdrawal without obsolete positive answers. These checks do not assert national or whole-plan completeness.

Render counts database responses sent outside its private network toward outbound bandwidth. The local publisher therefore verifies server-computed hashes rather than repeatedly downloading payloads. Ordinary deployment pipeline usage and workspace-wide bandwidth allowances still apply; unchanged service/disk plans are not a guarantee about the whole invoice. See [Render outbound bandwidth](https://render.com/docs/outbound-bandwidth). No additional paid compute or storage is provisioned by this pipeline.

## Repeated reference catalogs

The disk extractor interns identical provider groups across references in SQLite. Its content key includes the TIN fields, NPI-array presence, and every raw NPI with its multiplicity. Ordered reference links preserve first-use TIN behavior; multiplicities preserve rejected-NPI counters. Parsing still visits and validates the entire source, including unused and malformed references, JSON EOF, archive integrity, and source stability. No groups are sampled or skipped.

Small reference groups use a bounded buffer of at most 128 distinct NPI scalars and 64 KiB of UTF-8 content, spilling immediately to SQLite above either limit. Repeated small groups avoid redundant disk inserts. During resolution, the first selected use emits each exact group's memberships; later references add its stored rejection counters with their multiplicities. Unused groups never emit memberships.

Policy `5gb-ref-buffer-v7` retries resource-limit failures from prior extractors. Complete v5/v6 preparations remain reusable only through the existing full receipt, source-validator and plan-mapping checks. Unchanged embedded stale-date rejections remain blocked across this representation-only upgrade. The same SSD, time, memory, membership and cloud-capacity limits apply. Tests compare byte-for-byte output and counters with the original extractor, cover both buffer spill boundaries, and exercise 100,000 repeated groups under a 512 KiB scratch limit. Large-source acceptance still requires its own complete run.

## Download interruption and TOC version recovery

New downloads use unique, write-once staging files on the SSD. A small private Mini journal records their volume identity, directory/file inodes, owner and hashes of fsynced prefixes; it contains no source payload or transport query token. Mounted network/cap failures remove only that attempt's stage. After a disconnect or worker death, the next serialized run checks the original volume and reclaims a matching abandoned stage even though the new run uses a different directory. Recovery writes a removal receipt and preserves live writers, final files, unknown legacy partials, replaced paths and changed durable prefixes. The uncheckpointed tail remains unaccepted temporary data.

Deletion-only recovery may reclaim recorded partials below the free-space floor after exact UUID, mount and writability checks. Normal download and publication admission still requires the full 150 GB floor and 100 GB task budget. Missing storage never triggers an internal bulk fallback. Discovery failures also recheck the session guard so a disconnected SSD remains an expected deferral.

A completed-download journal can recover a lost caller receipt only when a freshly checked ETag and length match and the entire owned file still hashes correctly. This is transport recovery, not JSON/reference/coverage acceptance. Anthem parent TOC directories bind source identity and ETag separately; signing query renewal does not change identity, while an actual ETag change creates a new immutable archive directory. Prior parent TOCs and projections remain available for replay and rollback.

`tests/refresh-download-staging.test.ts` covers reconnection into a new run directory, durable-prefix corruption, inode/directory replacement, active writers, lost completion receipts and preservation of unrelated files. Unjournaled historical partials require separate ownership review and are never swept automatically.


## Shared exact plan mappings

`shared-plan-set-v1` keeps each distinct complete plan mapping once and associates every source file with its exact set. Every plan name, identifier type, identifier and market field remains intact. Reuse requires a content hash over binary-ordered, length-prefixed UTF-8 fields; different metadata cannot share an identity. The database independently hashes the actual stored fields before publication and on replay, returning only the digest and counts to Mini.

This is a separate protected opt-in (`shared-plans.json`) installed only after `/api/health` advertises the compatible reader. Existing per-file plan rows and all prior source archives remain unchanged. Search and provider queries combine both representations and retain active-generation and source-freshness rules. The shared mapping conveys no additional plan or network completeness. Reader rollback must preserve support for all published representations or explicitly withdraw incompatible generations first.

Three additive tables are initialized by the same guarded web startup, with SELECT/INSERT/DELETE grants for the restricted publisher. No new cloud service, job, disk, tier or replica is needed. New mapping sets reserve the larger of their full row estimate and three times their actual UTF-8 metadata bytes; a hash-verified existing set reserves only its new file association. The 2.5 GB application gate is checked again inside the atomic publication transaction. Reuse never bypasses the gate or source validation.

Current and rollback file associations protect their shared sets. Retiring an archive-verified owned generation may delete only its now-unreferenced mapping set; unrelated sets and legacy plan rows are not swept. Disconnects roll back both a new set and its file association. `scripts/eval-shared-tic-plans.ts` exercises the real disposable loopback database, including changed-content rejection despite equal counts, mixed legacy/shared queries, exact metadata, retention and withdrawal.
