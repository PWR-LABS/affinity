# guru coverage workspace

The guru-first homepage implements a guided coverage journey alongside a shared workspace. Discover separates employment from an actual individual or household employer offer; Coverage checks an exact doctor/plan pair; Compare annualizes user-declared employer or Medicaid premiums against a Marketplace amount; How supplies a replayable confirmation plan and official handoffs. The full screening, Marketplace, employer and selected Part D tools remain reachable. This is decision support, not enrollment or a complete Medicare comparison.

The guided journey works without a model, model credential or allowance. Its free-text task routing is deliberately simple and labeled guided mode. Source-backed answers come from existing application APIs. Connected guru is a separate optional conversational path, enabled only by operator configuration and the user’s checkbox. It carries bounded recent conversation and confirmed context, asks for missing facts, explains current tool evidence, and proposes explicit context edits or a supported check for confirmation. The server resolves applicable evidence through allowlisted application handlers; client prose and earlier conversation are not evidence authority. Model explanations remain fallible and are labeled AI explanations. The application computes premiums and renders source status independently. A suggested check is not a completed tool execution.

## Context and evidence

Household fields and selected medications live in a client context provider across site navigation, without URLs, localStorage or database persistence. Clearing guru also clears this in-memory selection store. Changing relevant inputs invalidates evidence cards and visibly supersedes earlier bound chat claims; changing source facts/status/date with the same inputs does the same, while a retrieval timestamp alone does not. Source-content fingerprints are change detectors, not authentication. Confirmed household-size changes reset the same-people premium basis through the central context writer, including full forms and conversational edits. Doctor, employer and plan names use existing explicit match selectors; a new search name clears its old identifier. Changing relevant inputs invalidates results; request sequence and snapshot checks prevent late responses from an earlier context becoming current. Existing full screening and Marketplace forms also invalidate their results on relevant changes.

Doctor evidence must match the requested NPI and plan identifier. Only a current, explicitly listed issuer result can receive a listing label. Absence, stale dates, unsupported dates and conflicting statuses stay unknown. An EIN may cover several benefit options, so a listing is not confirmation of the individual's actual option or a future-year promise. Source-internal date and lookup time are distinct. Full Marketplace results remain premium estimates with separate care-fit checks.

An employer or household-member offer is never inferred from employment. The new forms and guru withhold subsidized estimates until the user confirms there is no relevant employer offer; otherwise they direct the user to official affordability/minimum-value review while retaining state Medicaid and comparison handoffs. This is a limit of the local screening, not a finding that employed people cannot qualify. [HealthCare.gov explains the employee and household review](https://www.healthcare.gov/have-job-based-coverage/change-to-marketplace-plan/). No annual affordability threshold is hardcoded here.

Every public turn first reserves **$0.03 for Terra** or **$0.05 for another reviewed model** in the shared PostgreSQL ledger under a transaction advisory lock. Both aggregate UTC calendar-day and calendar-month caps apply. The ledger adds historical and new reservations at their original amounts. Concurrent clients share the same rows; restarting the app cannot reset the allowance. A repeated UUID cannot dispatch again. Reservations are retained after successful responses, timeouts, refusals or missing responses; there are no automatic retries or refunds. The reservation is conservative, not an invoice or actual per-turn cost. Withholding after allowance exhaustion affects AI availability; guided tools remain available.

The text-only request is bounded to 12,000 serialized UTF-8 bytes plus a 4,096-token framing allowance and 1,000 maximum conversational output tokens (800 for the earlier planner). At reviewed Terra rates, using the 30-minute cache-write rate for every input token gives an upper estimate of $0.02512. Public dispatch also checks the actual request envelope against its selected reservation and the reviewed rates before charging the ledger. Before reserving a public turn, `src/lib/guru/pricing.ts` checks the official OpenAI Standard pricing table. Each process refreshes upon demand at most daily after a successful check, and shares a single in-flight fetch among concurrent requests. A rate above its reviewed ceiling or a model removed from an otherwise recognized table disables that model. An unavailable or unrecognized document leaves the last successful check valid for up to seven days from that check, with a 15-minute retry interval. A cold process starts from the last manually reviewed date in source. The private evaluation planner uses the pinned review date and $0.05 reservation. The full most recent accepted user message is preserved through the composer’s 1,500-character limit. Up to eight recent messages are carried, with older messages bounded to 750 characters each and omissions explicitly marked; oldest messages are trimmed further when needed to fit the conservative upper reservation. Confirmed context and current evidence are never silently trimmed. Extended cache retention, images and provider-side tools are not requested. Requests use `store:false`; this is not a provider zero-retention guarantee. [Official structured-output guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

## Public beta allowance

The application defaults to **$100 per UTC calendar month** and **$5 per UTC calendar day**. Environment overrides may lower these limits; monthly values above $100 and daily values above $5 fail closed. With all-Terra traffic at $0.03 per attempt, these caps allow up to 3,333 attempts/month and 166/day. Each attempt at $0.05, including any earlier attempt in the window, uses more of the available cap. These are application dispatch ceilings measured in reservations. Expired pricing still fails closed. Enabling other AI endpoints requires inclusion in the same budget before release.

Each signed browser identity is limited to **3 attempts per rolling minute, 40/day and 50/month**. A separate shared-network backstop allows **10/minute, 80/day and 150/month**, limiting cookie-reset abuse to at most $7.50/month from a stable network. IPv6 addresses are grouped by /64; IPv4-mapped IPv6 is normalized to IPv4. All checks and the reservation insertion run under the existing PostgreSQL transaction lock. Failed, refused or lost provider calls retain their reservation and quota; blocked attempts create no reservation and dispatch no model request. Refresh, clearing the conversation, request UUID changes, multiple workers and server restarts do not reset stored counts.

This public app has no login: a browser/network is **not a verified person**. Clearing cookies and changing networks together can evade those identity limits, while the shared monetary cap remains. Shared workplaces, VPN exits and households can encounter the network limit together. Stronger person-level enforcement requires a separately designed sign-in/verification flow; do not claim that this anonymous system authenticates people. HTTP 429 carries a bounded reason and Retry-After, and the workspace offers guided tools without automatically retrying.

Privacy: `__Host-affinity-guru` is a signed random first-party cookie, Secure/HttpOnly/SameSite=Strict, valid for at most 31 days. Raw IP addresses and cookie values never enter the ledger; domain-separated HMACs use a dedicated stable server secret. Prior-month identifying hashes are nulled on the next successful reservation; accounting rows remain to preserve replay exclusion. These hashes are pseudonymous, not anonymous. Do not rotate the secret mid-month without reconciling quotas or holding AI disabled. Missing secret, invalid address, missing trusted ingress configuration or unavailable database fails closed.

### Hosted activation proof still required

`AFFINITY_GURU_CLIENT_IP_HEADER` accepts only `cf-connecting-ip` or a deployment-controlled `x-affinity-client-ip`. There is deliberately no guessed proxy-hop count or unconditional trust in arbitrary `X-Forwarded-For`. Before setting it, verify on **both** the custom domain and the service's direct hostname that an attacker-supplied copy is overwritten with the true ingress identity, and that direct origin access cannot bypass the trusted ingress. If this cannot be established, keep connected AI off until an authenticated identity or trusted proxy is available. [Render discusses forwarded client addresses](https://render.com/articles/how-render-handles-ddos-attacks); the generic guidance alone is not this deployment's spoof-resistance proof.

Provision the new random visitor secret through the existing protected server configuration path; never use the issuer source-proof key or put a secret in source control. Apply both ledger migrations through the authorized database path, verify existing database headroom, and exercise hosted quota denials with synthetic inputs before enabling public AI.
